# 开发流程

按改动大小安排工作，不要求每次都写计划、做固定轮数的审查或提交多份验收报告。安全、数据正确性和可复现的验证仍是基本要求。

## 日常步骤

1. 读相关实现与文档，确认要改什么、什么不改，以及如何验证。
2. 在工作分支做最小改动，保留与任务无关的现有修改。
3. 补充必要测试，同步受影响的配置、模板和文档。
4. 检查差异，按[测试安全边界](testing.md#测试安全边界)核实连接目标、凭据来源和副作用，只在隔离资源上运行对应验证，再修正发现的问题。
5. 说明结果、兼容性影响和已知限制，再按[Git 约定](git-commit.md)提交。

## 常见任务

### 新建项目

在脚手架根目录运行：

```bash
bash scripts/bootstrap.sh <target-dir> <app-name>
```

脚本会创建新目录并初始化新仓库，不执行依赖安装或数据库迁移。进入新项目后，按[快速开始](../getting-started.md)完成本地启动。参数与安全排除规则见[脚本说明](../../scripts/README.md)。

### 新增业务模块

```bash
bash scripts/new-module.sh user-profile user-profiles
```

生成器只提供骨架。继续完善表定义和仓储/服务逻辑，导出 schema，在 `ApiModule` 注册模块，并补测试。详见[模块开发](module-development.md)、[数据库](database.md)与[接口规范](rest-api.md)。不要为尚不存在的需求增加接口层、事件总线或队列。

### 开发前端与共享接口

管理后台在 `apps/admin-frontend`，手机端在 `apps/mobile-app`；按需启动 `pnpm dev:admin` / `pnpm dev:mobile`。公开契约和共享请求放在 `packages/contracts` / `packages/api-client`，变更时核对两端及 API；不直接共享服务端内部类型。环境变量、状态分工和移动端验证见[前端开发](frontends.md)。

### 修复缺陷或调整行为

- 先确认失效输入或时序，能自动复现的先补回归测试。
- 修复后验证正常路径、相关边界与错误处理；确认原本的失败场景能被测试检出。
- 公共接口或配置契约改变时，在文档与提交说明中明确兼容影响。
- 与当前问题无关的重构单独处理。

### 数据库变更

```bash
pnpm db:generate:mysql --name=<change-name>
# 检查生成的 SQL，再应用到本地开发库
pnpm db:migrate:mysql
```

迁移文件随代码提交，PostgreSQL 使用 `:pgsql` 命令。基础数据走自定义迁移，演示数据才用 seed。删表、删列或转换数据前，要确认影响范围、备份及恢复办法；不得把本地重置命令用于生产。详见[数据库](database.md)。

生产升级或破坏性迁移前，按[备份与恢复](../backup-and-restore.md)完成经授权的变更前备份并记录恢复点；这不是测试步骤，也不会由普通 CI 自动执行。

### 文档、配置和脚本

- 文档：核对描述、命令和链接，执行 `pnpm format:docs:check`，需要格式修复时使用 `pnpm format:docs`；不为改错字运行无关测试。
- 配置：同步所属应用的校验逻辑、`.env.example` 与配置说明；不要用示例覆盖真实 `.env`。
- 脚本/模板：在临时目录验证生成结果、拒绝覆盖与敏感文件排除，不操作真实业务数据。

## 验证范围

| 改动                           | 至少验证                                                         |
| ------------------------------ | ---------------------------------------------------------------- |
| 纯文档                         | 链接、示例路径与现有实现一致                                     |
| 工具函数或业务逻辑             | 相关单元测试、类型和静态检查                                     |
| 前端页面、导航或共享接口       | 对应应用与共享包的类型、静态检查和构建；按交互或协议变化补充验证 |
| 数据库、Redis、队列或连接管理  | 相关单元与真实依赖集成测试，包含失败及资源释放路径               |
| 应用装配、启动、部署或公开接口 | 相关端到端测试                                                   |
| 准备推送代码                   | 静态检查、构建、全量测试通过                                     |

```bash
pnpm lint:check
pnpm typecheck
pnpm build
pnpm test
```

`pnpm test` 包含 API 单元、集成、端到端测试、管理后台镜像测试及共享包单测，需要 Docker。`pnpm build` 构建整个工作区，手机端只导出 bundle / 静态资源，不包含原生签名、商店发布或真机验证。管理后台镜像测试验证静态部署和代理，不替代浏览器交互测试。开发时可只跑相关文件；测试分类、命令和覆盖率检查见[测试规范](testing.md)。上述验证要求不授权接触生产数据、外部写入接口或区块链主网；无法确认隔离时停止相关检查并说明原因，不把“未测试”写成“通过”。

## 风险较高的改动

涉及权限、密钥、资金、幂等、数据迁移或关键状态变化时，先列出相关失败场景，再补有针对性的测试和审查。必要时说明上线顺序、备份及恢复方案，并由负责人最终确认。

不固定要求审查轮数或报告数量。交付记录应足以说明：改动原因、关键验证及实际结果、兼容性影响、尚未覆盖的风险。内容简短时写在合并请求里；需要长期留存时放入 [reports/](../../reports/README.md)，不重复抄写多份。
