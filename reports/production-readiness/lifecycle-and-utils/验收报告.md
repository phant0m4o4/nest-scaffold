## 第 0 档：复现与循环审查

初始审查以异常时序和资源所有权为重点，结合本地依赖实现验证：

- 重试工具直接等待任务 Promise，取消后仍可能成功或永久挂起；异步重试回调同类。
- 随机字符串字符集为空或耗尽后拼入 `undefined`，重复字符集破坏无重复承诺。
- BullMQ 不负责关闭传入的共享 Cluster，原工厂没有关闭钩子。
- 队列并发为 0 时原实现不执行任何 Redis 操作，旧限制保留；小数和无穷值也被接受。
- Bottleneck 连接只转发 Redis 错误、不拒绝就绪 Promise，启动可无限等待。
- Bottleneck 退订内部异步操作没有被 `disconnect()` 等待，随后强断连接可能产生未处理拒绝。

修复后审查记录：

- 重试取消：独立检查 Promise 拒绝处理、取消与重试顺序、同步抛错和监听释放，未发现新增问题。
- 随机字符串：独立检查零长度、字符容量、重复权重和码点语义，未发现新增问题。
- Bottleneck：独立核对库内的连接所有权、终止标志、异常传播和运行中函数语义，未发现新增问题。
- 队列首轮回炉：初稿只保留 `QueueModule` 包装，误以为静态 imports 一定先注册。独立以真实 Nest `close()` 和替代 Provider 记录发现，业务模块先导入时仍是队列关闭 → owner 关闭 → Worker 关闭。原因是 Nest 容器提前插入动态 imports。调整为复用同一根配置动态模块并在动态 imports 中显式先导入；修正后需重过独立顺序检查与真实运行任务测试，不能用初稿单测绿灯代替。
- 队列回炉结果：根模块优先、业务模块优先、多个同步/异步业务模块的实际关闭顺序均复验通过；真实三主节点测试同时验证任务完成、Worker 关闭、队列关闭均早于 Cluster 关闭。原生 BullModule 混用仍可绕过约束，不宣称支持，具体限制见下文。
- 最终整份改动从边界与异常时序、资源所有权和范围/隐私三个视角复核：在明确的封装入口支持范围内，零新增阻塞问题；未涉及资金、密钥或业务持久状态迁移。单元、集成和端到端测试无跳过，无修改门槛。

依赖语义核对以本地锁定版本为准，并查阅 [BullMQ 全局并发文档](https://docs.bullmq.io/guide/queues/global-concurrency)、[Nest 生命周期文档](https://docs.nestjs.com/fundamentals/lifecycle-events) 和 [Bottleneck 2.19.5 连接实现](https://github.com/SGrondin/bottleneck/blob/v2.19.5/lib/IORedisConnection.js)。不同大版本的在线示例不直接作为本地实现依据。

- 随机字符串仍使用 Math.random，不作为安全凭据生成器；Unicode 保证码点，不保证多码点字素组合。
