# 里程碑任务验收约定（全局）

> **适用于所有里程碑的每一个任务**（以及同等风险的功能/修复 PR）。各 `M{n}-*.plan.md`（或项目内等价里程碑计划）实施前必须先读本文档；里程碑计划只写各任务「测什么、怎么人工验」，**完成定义与流程一律以本文档为准**，里程碑计划不得削弱本约定。
>
> 成文基线（审查时逐条对照，而非每次从零找坑）：**首选** [engineering-conventions.md](engineering-conventions.md)（工程约定 · 通用不变量清单）。写法细则见 [coding-standards.md](coding-standards.md)；代理行为与 Git 隐私见仓库根 [CLAUDE.md](../../../../CLAUDE.md)；专题见 testing / database / rest-api / git-commit。

**每个任务的验收分四档，四档全过任务才算完成。**

**按改动风险施力，不搞一刀切**：四档 + 四件产物是「错了会丢钱 / 丢数据 / 留后门 / 坏回归」类改动的完整流程；纯机械改动（改错字、显而易见的一行、纯文档）走轻量版——自审一遍 + 让相关自动化测试过即可，不必凑满四档。分级由交付方给出，但**把有风险的改动当机械改动放水视同违规**（与第 3 档的分级抽查权一致）。

**任一档失败即回炉**：失败所暴露的修复本身是新代码，修完从第 0 档对**改动面**重新过一遍，不打完补丁就直接重测——补丁常引入新问题。

开发生命周期中的「准备 → 实施 → 验证 → 交付」见 [workflows.md](workflows.md)；本文把其中的**验证 + PR 验收产物**写死。

## 0. 前置循环 review（进入自动化测试之前）

实现完成后先对**本次改动**循环审查——这是拦低级缺陷的第一道门，门槛要高。审查取**对抗式立场**（adversarial，默认代码是错的）：任务是构造让它出错的输入/时序去**证伪**它，而不是读一遍觉得合理就放行——读代码只暴露你想得到的错，跑起来才暴露你想不到的。

**只认三类问题**：正确性缺陷、与规格不符、安全/资金/幂等风险（风格与命名不在此列，除非影响正确性）。审查以 [engineering-conventions.md](engineering-conventions.md) 为对照——按其第 0 档快速对照表逐条断言「遵守 / 不适用 / 违反(附场景)」。

四条硬约束：

- **换视角，而非同一视角审多遍**：正确性 / 资金幂等 / 边界与异常时序 / 安全，各以一个视角独立扫一遍——同一视角重复审收益递减，不同视角才覆盖不同失效模式。风险越高，视角越多、越该让独立 AI 审查与自审交替（独立视角比同一个人多读几遍更能发现盲区）。
- **能跑就别只读**：凡涉及资金 / 状态迁移 / 幂等的路径，审查不止读 diff——构造边界输入实跑一次，或写一条能复现疑点的临时断言，把「我觉得对」变成「我看它对」。
- **每条发现必带可复现失效场景**：「什么输入 / 时序 → 什么错误结果」；坐实不了具体场景的模糊疑虑，要么补成场景、要么撤回。这条既逼审查者证伪自己，也压掉为审而审的噪声。
- **发现即修，修完回炉**：修复本身是新代码、常引新问题；修完从头对改动面（本次 diff 及修复所触达处，不必扫全仓）再审一轮，回炉那轮尽量换手 / 换视角，避免「自己修自己审」的盲区。

**退出条件——连续空轮，不是一轮干净**：最近一轮对整份 diff 换新视角审查、零新增上述三类问题，才允许进入测试档；**高风险改动**（资金 / 密钥 / 状态迁移 / 幂等）要求连续两轮零发现——单轮零发现可能只是没审到，不是没问题。每轮「用什么视角、发现什么、怎么修」一行记录，并入 PR 审核记录。此环节压掉的是低级缺陷，让后面的测试失败与人工审核只暴露真问题。

## 1. 自动化测试

沉淀进 `pnpm test` / CI，成为永久回归，不是一次性检查；能自动化的必须自动化。**分三步，「测前定清单」不许跳过、直接开写用例：**

- **① 测前——先定覆盖清单**：写用例前，从任务规格 + [engineering-conventions.md](engineering-conventions.md) 枚举出**本次必须覆盖的用例类别**——正常路径、边界值、失败与异常分支、幂等重放、并发/时序（按改动性质取用，不涉及的注明「无」）。用例照此清单设计，而非想到哪写到哪（呼应 CLAUDE.md「目标驱动」：先定义可验证目标，再写让它过的测试）。写法见 [testing.md](testing.md)。
- **② 测后——查覆盖是否充分**：测完不止「列测了啥」，要把实际用例**回对 ① 清单 + 规格**逐条标「覆盖 / 缺口」。**枚举出的必测类别必须全覆盖**；剩余缺口要么补上，要么**显式写明为何不测**（不可测 / 超范围 / 成本不值，附理由）——**绝不静默遗漏**。（「涵盖所有情况」落地为：该测的一类不漏、漏的每一处都有名有理由；可能输入无穷，但必测类别有限且必须穷尽。）
- **③ 发现问题→先全部修完→再统一回第 0 档**：本档测出的问题（用例变红、或为补覆盖而新写代码）**先一并修完，不逐个回炉**（逐条乒乓既慢又乱）；这批修复都是**新代码**，全部改完后**统一回第 0 档**对改动面重审一轮，再回本档重测——不打完补丁就直接放行。

①②合成的「自动化测试清单」随任务验收报告给出，并作为 PR 描述的一部分留档（格式见下方产物 2）。

## 2. 人工验收

**能自动化的不许滞留人工档**；剩下真需要人的，也要**用自动化工具驱动到最后一步**，把人的动作压缩到「只看结论、只下机器判不了的主观判断」。

- **自动化驱动到临界点**：一次性命令用脚本 / CLI 串起来跑；前端 / 页面用**浏览器自动化**（如 Playwright；headless=无界面后台运行）导航到目标状态、截图或抓 DOM（Document Object Model，页面元素树）。「启动 → 操作 → 取证」整段自动化，人只在最后看产物（截图、命令输出、日志片段），而不是自己敲命令、自己点页面。本脚手架后端常见：`pnpm lint && pnpm build && pnpm test`、按需 `pnpm test:e2e`、迁移/种子命令输出。
- **真人工残留只剩视觉 / 交互 / 主观判断**：纯「这页长得对不对、交互顺不顺、文案通不通」这类机器判不了的，才留给人；能被断言覆盖的一律推回第 1 档。
- **必须标『请着重看这几处』**：像第 3 档审核导读一样，把人工验收做成**有指向的清单**——明确「看这张截图的哪块区域 / 这段输出的哪一行 / 这个交互的哪一步」，而不是甩一句「自己去点点看」。
- 执行的**一次性命令 + 实际输出**留档（见产物 3）：是真跑出来的结果，不是「预期」。

## 3. 代码审核

每任务独立分支，完成后发 PR、审核通过才合并（见 [git-commit.md](git-commit.md) / CLAUDE.md 规则 A.4）。GitHub 仓库建立前的任务用本地 diff 自审补记。

**通用审核清单，逐条过：**

- 实现与任务规格**逐条对照**——规格有的都做了，做了规格没有的要么删要么回写规格；
- 对照 [engineering-conventions.md](engineering-conventions.md) 通用不变量逐条过——底线一条没破；
- 未越界：比对**该里程碑计划的「明确不做」清单**（若有），不提前实现后续里程碑内容；
- **无任何密钥、真实端点、私人信息入库**（`.env` 只有 example；供应商 key 绝不进 git；本机路径/个人信息/AI 署名也不进，见 CLAUDE.md 规则 A）；
- 结构与命名符合仓库骨架约定（见 [architecture.md](architecture.md) / [coding-standards.md](coding-standards.md)），依赖没有随手乱加；
- 测试真实有效：断言不是摆设、无 skip、失败场景真的会红（可抽一条改错预期跑一次验证）。

**交付方必须在 PR 描述里附「审核导读」**，把改动按审核强度分两级，让人工时间花在刀刃上：

- **重点审**（逐行读）：资金/密钥相关逻辑、状态迁移与幂等、边界与异常分支、手写的核心算法、安全约束的实现落点、**一切规格外偏差**——凡「错了会丢钱/丢数据/留后门」的代码；
- **看一眼**（扫过即可）：脚手架与模板文件、照抄官方 recipe 的配置、自动生成物（lockfile、fixtures、drizzle meta）、纯声明式内容（依赖清单、占位组件）——凡「错了构建/测试自然会红」的代码。

分级由交付方给出但不由交付方说了算——审核人对「看一眼」部分保留抽查权，发现分级不实（把该重点审的塞进看一眼）视为审核不通过。

可先用 AI 审查辅助初筛，**人工最终拍板**；审核结论留在 PR 记录中。代码审查判断不得由代理代批（CLAUDE.md 规则 A.4）。

## PR 描述必含四件产物

每档一件，**缺任一件审核人直接退回，不进入代码审阅**：

1. **（第 0 档）循环 review 记录**：每轮「用什么视角、发现什么、怎么修」，直到收尾的连续空轮（高风险改动两轮）；
2. **（第 1 档）自动化测试清单**：每用例一行「测的行为 + 断言内容」；并附**测前覆盖清单与实际用例的对照**——必测类别全覆盖、每处缺口有名有理由；
3. **（第 2 档）人工验收记录**：自动化驱动到临界点的**命令 / 脚本 + 实际输出 / 截图**（不是「预期」，是真跑出来的结果），并标出**请着重看的几处**；纯自动化、无人工档的任务注明「无」；
4. **（第 3 档）审核导读**：重点审 / 看一眼 两级清单及理由。

PR 描述可摘要并链到下方入库文件，避免产物只活在会话里。

## 报告与提交节奏

**逐档出报告，别攒到最后**：每档一过完就产出该档报告（即上方四件产物中对应的那件），让进度逐档可见、问题早暴露——而不是四档闷头做完再一次性交。某档触发回炉，补一句「回炉原因 + 修了什么 + 重过结果」即可，不推翻已出的报告。

**四档全过后，出一份总结性验收报告——它是四份逐档报告的完整整合版，不是有损摘要**。逐档报告**原样并入、一件不删**，在其之上再加三样跨档汇总：

- **交付物清单**：改了 / 加了哪些文件，各自作用；
- **规格偏差回写**：做了规格没有的 / 规格有没做的，各自去向（删除 or 回写规格）；
- **改动面自查**：纯本任务、无越界、无密钥 / 真实端点 / 本机与个人信息入库。

即：总结报告 =（四份逐档报告全文）+（交付物清单 + 偏差回写 + 改动面自查）。压缩细节等于让审核人回头翻散落各处的逐档报告，违背「一处看全」的初衷。

**报告出完，询问是否提交——不自动提交**（呼应 CLAUDE.md / 用户规则：只在用户明确要求时提交），并一并给出建议的 commit message。

纯机械改动走轻量版（见开头「按改动风险施力」）：一段话说清改了啥 + 相关测试过即可，不必套满逐档报告与总结结构。

## 入库落点

按任务一目录，报告与取证放一起：

```
reports/<里程碑>/<任务>/
├── 验收报告.md          # 总结性验收报告（含四档全文 + 三样汇总）
└── evidence/            # 截图、命令输出摘录等（可选）
```

示例：`reports/m0/T1/验收报告.md`。目录约定见仓库根 [reports/README.md](../../../../reports/README.md)。

里程碑计划文件建议放在项目约定路径（如 `docs/milestones/M{n}-*.plan.md`）；计划中只写「测什么、怎么人工验」，完成定义指向本文档。
